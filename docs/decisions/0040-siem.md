# 0040. SIEM: Sigma rules over events, and a signal is one rule on one host

- **Decision:** Proposed
- **Implementation:** In progress
- **Where:** `siem` takes events as JSON, runs Sigma rules over them and keeps signals (`ghcr.io/openasy/siem`). Collection by an agent, correlation across rules and links to Logs, Alerts and Incidents are planned.
- **Priority:** High
- **Area:** Architecture

## Context

A SIEM is where security-relevant events from everywhere are compared with what is known to be wrong, and where what it finds is worked until it is closed. Two things make products in this space fail. They drown people: one failed login is an event, a thousand are one thing to look at, and a product that shows a thousand rows is switched off. And they lock people in: detection content written in a vendor's language belongs to the vendor.

Sigma is the open, widely shared format for detection rules, with thousands of maintained rules for the logs teams already have. A product that reads Sigma as it is can use that work from the first day, and a team that leaves takes its rules with it.

## Decision

- **Rules are Sigma, as written.** Rules are stored as the text the author wrote, Sigma YAML or JSON, and read when the product starts, so an upgrade that changes how a rule is read never rewrites it. The first release reads selections of fields with the modifiers contains, startswith, endswith, re and all, keyword lists, and conditions with and, or, not, parentheses and `1 of`, `any of`, `all of` over names, patterns and `them`. What is not read yet (aggregations, timeframes, other modifiers) is refused with a message that names it. A rule is never silently weakened.
- **The YAML reader is our own and small.** It covers what Sigma rules use and refuses the rest of YAML (anchors, tags, flow maps, several documents), which keeps a parser with a long history of surprises out of a product that reads rules from outside. A rule that needs more can be written as JSON.
- **Events come in as flat JSON** from shippers and scripts, one or an array, with an ingest token that can send events and nothing else. They are kept for 30 days in the product's SQLite file (ADR 0011). Nested values are refused at the door, so rules and search see the same fields and a field name means one thing.
- **A rule is checked before it is live.** Testing runs rule text over the newest events and shows what it would have matched, without keeping or alerting anything. A rule that fails on an event is noted on the rule and skipped; it never stops events from being kept.
- **A signal is one rule on one host within a window** (60 minutes by default). It has a count, the first and last time, and the first five events. A signal that is closed or marked as a false positive stops collecting, so the next match is a new signal and a new decision. A false positive needs a reason.
- **Regular expressions are limited.** A pattern is at most 512 characters, values longer than 4096 characters are cut before it sees them, and patterns that can backtrack without end are refused, since rules come from outside and run on every event.
- **The first release** has events, rules (add, change, switch on and off, test), signals with the four statuses, search, and the API and UI for them. Collecting from hosts without a shipper, correlation of several rules into one story, links to Logs, Alerts and Incidents, and Sigma aggregations follow, each when it is built.

## Consequences

- Rules run in the application, on every event, before it is answered. At small volumes this is simple and safe; at large ones it is the first thing to move out of the request, and the record says so now so that nobody is surprised.
- Not every Sigma rule in the wild runs yet. The UI and the API say which part is missing, and teams can start with the large share that needs only selections and conditions.
- Field names in rules come from the rule's logsource, and events must carry them. Mapping from a shipper's names to Sigma's (for example Windows event fields) is the shipper's configuration for now, and a product feature later.
- Signals hold copies of event ids, not events. When events are deleted by retention, an old signal keeps its counts and times but not its samples, and says so.
- Events can hold personal data and secrets. Viewers read them, retention deletes them, and the documentation says so (ADR 0015).
