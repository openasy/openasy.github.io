# 0069. WAF: Coraza and the OWASP Core Rule Set in the request path, sites start in detection-only mode

- **Decision:** Proposed
- **Implementation:** In progress
- **Where:** `waf` runs Coraza with the OWASP Core Rule Set in a small Go proxy inside its container, in front of each site's application; it manages sites, the rule set's paranoia level, threshold and groups, exclusions and custom SecLang rules with virtual patches, and shows traffic and every request a rule matched, with the rules and the anomaly score (`ghcr.io/openasy/waf`). Rules made from DAST findings through a link, response inspection, address blocks, rate limits and events to SIEM are planned.
- **Priority:** High
- **Area:** Architecture

## Context

Fixing a flaw in an application can take weeks; attackers start the day it is found. A web application firewall in front of the application refuses requests that look like attacks until the fix ships. ModSecurity's rule language, SecLang, and the OWASP Core Rule Set that is written in it are what security teams already know and tune; Coraza runs both, is maintained by OWASP, and is a Go library under Apache-2.0. A rule engine of our own would have neither the rules nor the years of tuning behind them. The danger of a WAF is the other way round: strict rules block real users, and a team that turns one on and breaks its shop turns it off for good.

## Decision

- **The engine is Coraza with the Core Rule Set, in the request path.** A small Go proxy in the repository (`proxy/`) wraps Coraza and the rule set as `coraza-coreruleset` embeds it, pinned by `go.sum`; it is built with a pinned Go toolchain checked against its checksum (ADR 0027) and runs as a child process of the application, which restarts it when it stops and reports it in `/readyz`. Coraza reads only the embedded rule set and the SecLang the application writes, never files of the host.
- **The proxy holds no settings.** The application renders each site's SecLang (the rule set with the site's mode, paranoia level and threshold, its exclusions and custom rules) into one JSON file on a tmpfs and sends SIGHUP. A site whose rules did not change keeps its compiled rules; a change the proxy cannot compile is refused with Coraza's error, and the rules before it keep serving.
- **A site starts in detection-only mode.** Every rule runs and what it matched is reported as "would block", but nothing is refused, so turning WAF on cannot break an application. Switching to blocking is for admins and shows how many requests it would have blocked in the last seven days first. Blocking follows the rule set's anomaly scoring: a request is refused when its inbound score reaches the site's threshold, 5 by default, and gets 403 with a reference.
- **Sites** are host names and an upstream; each host belongs to one site, and `*` takes the rest. The client's address is the peer's, or from `X-Forwarded-For` only when the peer is in `OPENASY_TRUSTED_PROXIES` (ADR 0026). TLS ends at the install's proxy in front.
- **Tuning is in the open.** Exclusions leave a rule, a range or one part of the request out, for a site or under a path, with a reason; they are generated SecLang from checked fields. Custom rules are SecLang, after the rule set, limited to SecRule and SecAction, ids 1000000 to 1999999, phase 1 or 2, and a list of operators and actions: those that read files, look up DNS, run programs, change the engine (`ctl`) or let a request skip every other rule (`allow`) are refused. A virtual patch for a DAST finding is such a rule, written from a path, a parameter and an attack class. Editors tune; admins manage sites (ADR 0003).
- **What matched is kept, and what it carried is not.** The proxy reports every request a rule matched, with each rule, the variable and value it matched and the anomaly score, and counts every request per site; SQLite keeps them (ADR 0011) for 30 days by default. Values of parameters, cookies and headers whose names look like a secret are dropped before they leave the proxy, since a password with a quote in it matches the SQL injection rules. At most 500 reports a second are kept; the rest are counted and dropped, never slowing requests down.
- **The first release** has sites with detection and blocking, the rule set per site with its paranoia level, threshold and groups, exclusions, custom rules with virtual patches, Traffic and Blocked. Rules made from DAST findings through a link to DAST (ADR 0001), response inspection, address blocks and threat-intel lists, rate limits, testing a rule against past traffic, hits per exclusion, rule set updates between releases and blocked attacks as SIEM events follow, each when it is built.

## Consequences

- The product is in the request path of every site it protects: when the proxy is down, the sites do not answer. It is restarted at once, and `openasy_waf_engine_up` is for a system other than WAF to watch.
- One container runs two processes, and each site's compiled rule set takes memory; the use per site is to be measured in CI.
- The rule set changes with a release of WAF, not on its own; a new rule set version is tested like any upgrade.
- SecLang is part of what people write against WAF: a Coraza release that reads a custom rule differently is a breaking change for us, and custom rules are compiled against the real proxy in CI.
- Every viewer reads attack payloads and client addresses; per-site access can follow if teams need it.
