# 0035. Logs: VictoriaLogs inside, logs sent to it or read over SSH

- **Decision:** Accepted
- **Implementation:** Not started
- **Where:** Planned as `logs` (`ghcr.io/openasy/logs`) and `logs-agent` (`ghcr.io/openasy/logs-agent`).
- **Area:** Architecture

## Context

Logs is where people search what happened on their hosts and services, and what SIEM, Alerts and Incidents read from later. Three goals recommend it. It must follow the rules every product follows: one container (ADR 0016), small enough to run on a small server (ADR 0028), and nothing installed on hosts (ADR 0031). ADR 0011 keeps SQLite for configuration and state and leaves large time series to their own storage engine; this record picks that engine and decides how logs arrive.

The options for storage were:

- **VictoriaLogs** is one static binary under Apache-2.0, built for amd64 and arm64. It stores logs compressed by column, indexes every field without a schema, and is queried with LogsQL. It runs in tens of megabytes at idle and accepts the Loki, Elasticsearch bulk, OpenTelemetry and JSON lines formats that existing shippers already speak. It has no users, roles or interface of its own worth keeping.
- **Grafana Loki** is widely used, but indexes only labels, so a search for text in a large range reads everything. Its smallest setup still wants object storage for long retention.
- **An engine of our own** on SQLite FTS5 or Parquet would have no dependency, but compression, retention and fast search over terabytes would all be ours to build and to get right.

Logs reach a central place in two ways. Teams that already run rsyslog, journald forwarding, Vector, Fluent Bit or an OpenTelemetry collector can send them. Hosts that run nothing of the kind still keep their logs in journald and in Docker; under ADR 0031 we may read those, but not install a shipper.

## Decision

- **Storage is VictoriaLogs, inside the product's container.** The `logs` application starts it as a child process, listening only on `127.0.0.1`, with its data in `/data/vlogs` next to the SQLite file that holds sources, pipelines, saved views, people and settings. Nobody reaches VictoriaLogs directly: every read and write goes through the product, which signs people in with `@openasy/auth`, checks roles and tokens (ADR 0003), and records searches in its audit log. The binary is a pinned release, checked against its published checksum when the image is built (ADR 0027).
- **Search uses LogsQL as it is.** The query bar, saved views and the API take LogsQL, with facets for level, host and service built on top. We do not invent a query language that would have to be translated and would drift.
- **Logs are sent to the product** on receivers that are off until enabled, each with its own ingest token:
  - Syslog over TLS (RFC 5424 and RFC 3164) on 6514, with a certificate from a mounted file or one the product makes and shows the fingerprint of. Plain Syslog on 514 over TCP or UDP is a separate switch, off by default (ADR 0013).
  - OpenTelemetry logs over HTTP, and the Loki push, Elasticsearch bulk and JSON lines formats, so Vector, Fluent Bit, Promtail, Winlogbeat and OpenTelemetry collectors work with their own outputs.
  The product checks the token, applies the source's pipeline and writes the result to VictoriaLogs in batches.
- **Hosts that send nothing are read by `logs-agent`**, which works like `infra-agent` (ADR 0031): installed once per network, it connects out to the product, enrols with a one-time token, holds its own SSH certificate authority, and reads hosts as the unprivileged `openasy` account with 5-minute certificates. It runs `journalctl --after-cursor -o json` and, where the Docker switch is on, `docker logs --since`, keeps the cursor per host, and reads every minute by default. Reading the system journal needs the `openasy` account in the `systemd-journal` group, which is a named, opt-in privilege; without it only that account's own journal is readable and the UI says so. The agent masks values that look like passwords, tokens or keys before they leave the network.
- **Pipelines** turn raw lines into fields per source: parse JSON, Syslog and a regular expression, map severity to level, mask, drop and sample. They run in the product before storage, so what is stored is what was meant to be kept.
- **Retention** is 30 days by default and set per installation. Disk use is shown against the volume, and the oldest days go first when the disk is nearly full rather than the product stopping.
- **The first release** has the Explorer with facets and a volume chart, live tail, saved views, pipelines, the receivers above, `logs-agent`, retention, links from a host to Infrastructure (ADR 0001), and a threshold on a saved view that calls a signed webhook (ADR 0023). Archives to an S3-compatible write-once bucket for 400 days with rehydration, patterns, and routing to SIEM and Alerts follow, each when it is built.

## Consequences

- One container still holds the product, but it runs two processes. The application supervises VictoriaLogs, restarts it, and reports it in `/readyz` (ADR 0017); the image grows by the size of one binary.
- Logs is a product with large data, so the default budget of ADR 0028 does not apply. It publishes its use at 1 GB and 10 GB of logs a day instead, measured in CI.
- Logs hold personal data and sometimes secrets. Masking runs in the agent and in pipelines, searches are audit-logged, and the product's security page says that anyone with the viewer role reads every log it keeps (ADR 0015). Per-source access can follow if teams need it.
- Read over SSH, logs arrive about a minute late; live tail of those hosts is a tail of minutes, not seconds. Teams that need seconds send them instead, and the UI shows which way each host arrives.
- A host read by both Infrastructure and Logs trusts two certificate authorities, one per agent. Whether one agent per network should serve every product that reads hosts is left to its own record.
- LogsQL is part of our API (ADR 0024): a breaking change in VictoriaLogs' language is a breaking change for us, and upgrades of the binary are tested against saved views in CI.
