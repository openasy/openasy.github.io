# 0036. SAST: Opengrep scans every pull request, and only what is new blocks it

- **Decision:** Proposed
- **Implementation:** In progress
- **Where:** `sast` takes SARIF from CI, compares it with the default branch and keeps triage (`ghcr.io/openasy/sast`). `sast-agent` and the forge checks are planned.
- **Priority:** High
- **Area:** Architecture

## Context

SAST reads source code for flaws before it ships. People meet it in two places: on a pull request, where it must be fast and say only what the change introduced, and in a repository's overview, where it shows what is already there. A tool that reports every old finding on every pull request is switched off within a week. It must also follow the rules every product follows: one container (ADR 0016), small enough for a small server (ADR 0028), and no host-side surprises (ADR 0031).

The options for the engine were:

- **Opengrep** is an open fork of Semgrep's engine under LGPL-2.1. It reads rules written as code patterns in YAML, covers the languages teams use (JavaScript and TypeScript, Python, Java, Go, Ruby, PHP, C#, Kotlin, Rust and more), and reports in SARIF. It parses code and never runs it.
- **Semgrep Community Edition** has the same lineage, but its published rules carry a licence that limits use in a competing hosted service, and its roadmap is led by one company.
- **CodeQL** is deep, but free only for open source repositories, and its queries are not ours to ship.
- **An engine of our own** would be years of language grammars before the first useful finding.

## Decision

- **The engine is Opengrep, a pinned release** checked against its published checksum when the image is built (ADR 0027). Rules are YAML files in the Opengrep format. We ship only rules whose licence lets every OpenAsy user run them, say where each came from, and let teams add rules of their own under Rules. We do not invent a rule language.
- **Repositories are connected, not mounted.** An owner connects GitHub, GitLab, Gitea or Bitbucket with an app installation or a token with the fewest scopes the forge offers: read the code, write a check and a comment. Webhooks (signed, with a secret) start a scan on every push and pull request. Tokens are stored encrypted with the key that lives outside the data volume (ADR 0021) and are never returned by the API.
- **Code is untrusted input and is scanned apart from the product.** A scan runs in `sast-agent`, a separate container that connects out to `sast`, enrols with a one-time token and asks for jobs (the pattern of `infra-agent`, ADR 0031). The agent clones into a tmpfs, runs Opengrep as an unprivileged user with no other network than the forge, a memory limit and a time limit, then deletes the clone. `sast` holds no source code at rest and no scanner; a hostile repository can at worst waste one agent's time (ADR 0022).
- **Pull requests see what they add.** Every finding has a fingerprint that survives moved lines (rule, file path and normalized code). A pull request is compared with the commit it branches from; only findings that are new block it or show in its comment. The default branch is scanned in full on every push and keeps the baseline.
- **Policies decide what blocks.** A policy per repository or group sets the lowest severity that fails the check, which rules are off, and whether a finding in tests blocks. The check result is posted to the forge as a status check, with a short comment that links each finding.
- **Triage is kept, not lost.** A finding can be marked fixed, a false positive or accepted risk, always with a reason, who decided and an optional expiry. Suppressions are per fingerprint, so the same finding on another branch stays quiet, and they show in the audit log.
- **SARIF goes both ways.** Findings export as SARIF 2.1.0, and SARIF from other tools can be imported for a repository, so teams that already run another analyser see everything in one list.
- **Secrets are not this product's job.** Finding keys and tokens in code belongs to Secrets, which `sast` links to by repository, so the two share a pull request check instead of repeating each other.
- **The first release** has Repositories, Pull requests, Findings with triage, Rules (shipped and own), Policies, the forge checks above, SARIF export and import, and the agent.

## Consequences

- Two containers again, the second needing a clone of the code. The agent runs where the repositories can be reached and needs nothing from the product's network.
- Analysis is pattern and data-flow within a function or file, not whole-program. It finds many classes of flaw quickly and misses some that CodeQL finds. The UI says which rules are pattern-only, and the site does not claim more.
- Rules are the product's quality. A noisy rule is a defect: each shipped rule has a test file with code it must flag and code it must not, run in CI (ADR 0029).
- Forge APIs differ. Each forge is its own adapter behind one interface, tested against a fake server in CI; GitHub and GitLab come first.
- Findings contain snippets of code. Snippets are stored with the finding, shown only to people who may read that repository's findings (ADR 0003), and removed with the repository (ADR 0015).
