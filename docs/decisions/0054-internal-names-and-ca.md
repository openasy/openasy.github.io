# 0054. Split-horizon names and an internal CA over the VPN

- **Decision:** Proposed
- **Implementation:** In progress
- **Where:** `vpn` keeps the inside view of `VPN_DNS_DOMAIN` (Access, Internal names; `/api/v1/internal-names`), lets an IP group or a device turn it off, and sends it with each server's config; `vpn-server` answers it on the tunnel's first address, asks `DNS_UPSTREAM` for the domain's other names unless `VPN_DNS_FORWARD=false`, and pushes that resolver for the domain alone. `vpn` runs the internal CA: a root with Name Constraints for the domain and no IP address, its key sealed, made again for a new domain; it issues certificates by hand from Access, Internal CA, and over ACME at `/acme/directory` with External Account Binding and http-01; it serves the root as PEM, a Windows `.cer` and an Apple profile. The install builder sets the domain, and with Products only on the VPN gives every product but VPN and Identity a certificate over ACME and no public name. The end-to-end test resolves inside and outside names through the tunnel, has a real Caddy get a certificate over ACME, opens both HTTPS sites there trusting only the internal root, and gets no answer off the VPN. Sending issued certificates to Certificates and names from the hosts file are not built yet.
- **Priority:** High
- **Area:** Security

## Context

The tools an install runs, OpenAsy's products among them, are for its own people. Today each one needs a public name, a public certificate and a port open to the internet, so the sign-in screen is the only thing between the internet and the tool. Teams that already give their people a VPN want those tools at names of their own domain, such as `logs.youreply.com.tr`, that resolve to inside addresses only on the VPN and carry a certificate the browser accepts, while the domain's public names keep working everywhere. This is split-horizon DNS with a private CA. Today `vpn-server` pushes routes and, for a full tunnel, the default gateway; it pushes no DNS, and there is no CA but the one that signs VPN devices.

## Decision

- **An option, off by default.** `VPN_DNS_DOMAIN` names the install's internal domain, such as `internal.yr`. Unset, nothing changes: no DNS is pushed, no DNS server runs and no internal CA is made. Set, it is on for every device, and an IP group or a person's device can turn it off; those devices keep the connection they have today. Addresses keep working either way: internal names add to them.
- **The domain is the install's.** Usually its own public domain, such as `youreply.com.tr`, or a domain that exists only inside, such as one under `.internal`, which ICANN keeps for private use; not a single word that may become a public top-level domain. A browser may search for a name under a top-level domain it does not know the first time; typing `https://` or a bookmark avoids that.
- **vpn-server holds the inside view of the domain.** A small DNS server, built into `vpn-server` with no dependency, listens on the tunnel's first address on port 53, UDP and TCP. A name with a record from `vpn` is answered from that inside view alone. Any other name in the domain is asked of the location's resolver (`DNS_UPSTREAM`, by default the host's), so `www` and mail keep their public records on the VPN: split-horizon. For a domain that exists only inside, `VPN_DNS_FORWARD=false` answers that such names do not exist. Every other domain is refused, so the server is never an open resolver. Devices get it as the resolver for the domain alone (`dhcp-option DNS`, `DOMAIN-ROUTE`, and OpenVPN 2.6's `dns server ... resolve-domains`), so every other name still goes to their own resolver. The firewall lets the tunnel reach port 53 on that address and nothing more on the server (ADR 0022).
- **Names come from `vpn`.** An Internal names page and API keep A, AAAA and CNAME records. Servers in the install's hosts file (ADR 0052) whose address is an IP are added as `<name>.<domain>`, and stay as the file says.
- **An internal CA, held in `vpn`, that can sign nothing else.** A root separate from the one that signs VPN devices, its key sealed with the product's key (ADR 0021). It carries a critical Name Constraints extension that permits only the domain: a device that trusts it trusts it for those names alone, and a stolen CA key cannot impersonate any other site. It issues server certificates for names in the domain: first from the page and API, then over ACME, with `dns-01` answered by `vpn-server`'s own DNS, so Caddy, certbot or cert-manager inside get and renew theirs by themselves. Certificates it issues are sent to Certificates (ADR 0046) for their expiry.
- **The root reaches devices once.** A device trusts the CA only after its root is installed: the VPN self-service page offers it as a macOS and iOS profile, a Windows certificate and a PEM, at an address an MDM can fetch, with the steps for each system. OpenVPN cannot install it.
- **OpenAsy itself can live only on the VPN.** The install builder offers two ways to reach the products: over the internet, at public names with certificates from Let's Encrypt, as today, or only over the VPN, at internal names with certificates from the internal CA and no port open but the VPN's. Because a first device needs a config before it can connect, only-VPN keeps the VPN panel and Identity, which signs people in to it, at public names by default; an install can close them too, and then an admin hands each person their first config (`openasy-vpn devices add ... --out`) and later devices are added from inside.

## Consequences

- Tools need no public name, certificate or open port; on the VPN they look like any site, with a padlock.
- One more trust root on every device, limited to one domain. Installing it is a step for each device, or for the MDM.
- `vpn-server` becomes a DNS server for its domain, and `vpn` a CA: both carry keys and answers that must stay right, and both are tested end to end.
- A device without the root still reaches the names, with a certificate warning; one with the option off reaches tools by address.
