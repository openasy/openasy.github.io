# 0037. DAST: scanners run in an agent, and only on targets you have proven are yours

- **Decision:** Proposed
- **Implementation:** In progress
- **Where:** `dast` keeps targets with proof of ownership, the queue of scans and their schedules, and takes SARIF reports from ZAP and Nuclei (`ghcr.io/openasy/dast`). `dast-agent` runs ZAP and Nuclei in passive, standard and full profiles and verifies targets on private addresses (`ghcr.io/openasy/dast-agent`), signed in with a target's login, a header or a form. OAuth client credentials and the PDF report are planned.
- **Priority:** High
- **Area:** Architecture

## Context

DAST attacks a running application the way a stranger would, and finds what only shows at runtime: missing headers, injection, broken sign-in, exposed paths. That makes it dangerous by design. A scan that points at the wrong address attacks someone else; an active scan of production can corrupt data or take it down; credentials given to a scanner are credentials to the application.

The scanners are heavy. ZAP is a Java program that wants hundreds of megabytes; Nuclei is one static binary with thousands of templates. The target is often reachable only from inside a network, not from where the product runs. Both facts rule out a scanner inside the product's own container (ADR 0016, 0028).

## Decision

- **Two engines, each for what it does well.** ZAP crawls the application, including single page applications, and runs passive and active rules. Nuclei runs template checks for known exposures and misconfigurations. Both are pinned releases checked against their published checksums (ADR 0027). A finding says which engine and rule found it, and only findings with a request and a response as evidence are marked confirmed.
- **Scanners live in `dast-agent`.** It is installed once per network, connects out to `dast`, enrols with a one-time token and asks for jobs (ADR 0031, as `infra-agent` does). It can reach targets that `dast` cannot, and `dast` stays a small application with no scanner in it. The agent runs as a non-root user with a read-only root filesystem and no capabilities (ADR 0022).
- **A target must be proven before it is attacked.** Adding a target asks the owner to show control: a DNS TXT record or a file under `/.well-known/openasy-dast`. Until then only a passive baseline runs. Targets on private addresses are verified by the agent that can reach them. Redirects that leave the target's host are not followed, and scope rules (include and exclude paths) are enforced by the agent, not only by the scanner.
- **Safe by default.** Scans are `baseline` (passive only), `standard` (adds safe active rules) or `full`. `full` is never the default, asks for a confirmation that names the target, and is refused on a target marked production unless an admin allows it in that target's settings. Every scan has a request rate and a time limit, and can be stopped; stopping is immediate.
- **Auth profiles hold the way in.** A form login, a bearer token, an API key header or an OAuth client credential per target, with the secret sealed with the key outside the data volume (ADR 0021) and sent only to the agent running that scan. Secrets never appear in evidence: headers and bodies are masked before storage. Roles of the application can be added as several profiles, so a scan can compare what a user and an admin can reach.
- **Schedules and pull requests.** A schedule runs a scan on a cron expression, or after a deploy event sent to the API (ADR 0014). A scan can fail a pipeline by returning exit status from a small CLI that calls the API, with the same severity policy as a dashboard check.
- **Findings are triaged like in SAST** (ADR 0036): fixed, false positive or accepted risk, with a reason and an expiry. A finding is the same finding across scans, so a fix shows as closed in the next scan, and a returned flaw reopens.
- **The first release** has Targets with verification, Scans (baseline, standard and full), Findings with evidence, Auth profiles, Schedules, the agent, and a report as PDF and SARIF.

## Consequences

- Another agent to run, with a heavy image. `dast-agent` publishes its use for each scan type instead of the default budget of ADR 0028.
- Verification means a first scan takes a few minutes of setup. That is the price of never being the tool that was used to attack a stranger, and the UI and site say so.
- Active scans can still break a fragile application. Defaults, rate limits and the production lock reduce that; they do not remove it, and the documentation tells teams to scan staging.
- Evidence holds real responses, which may contain personal data. It is masked, kept for a retention period set per installation, and removed with the target (ADR 0015).
- Findings from ZAP and Nuclei overlap. They are merged by URL, parameter and weakness class, so a flaw found twice is one finding with two engines.
